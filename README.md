# 结算对账与计划对照台

面向结算团队的小工具，两个功能共用同一份结算样表数据：

1. **每日流水核对**：对账员按结算日上传支付渠道流水 CSV，与夜间入库的
   `settlement_orders` 按订单号核对，输出差异报告；
2. **SQL 计划对照**（保留）：在同一事务快照里对比默认计划与
   `SET LOCAL enable_nestloop=off` 的实际执行效果。

## 快速开始

```bash
docker compose up --build
```

打开 <http://localhost:8000> 。首次启动时数据库会自动建结算样表、灌入
100 万行随机订单（约需半分钟）并写入 2026-11-20 的确定性对账演示数据，
`web` 会等 `db` 健康检查通过后再起。

重新初始化样表数据：

```bash
docker compose down -v && docker compose up --build
```

## 每日流水核对

### 用法

1. 在「每日流水核对」页选择结算日、上传渠道 CSV（UTF-8，表头
   `order_no,merchant_id,amount,fee`，允许额外列）；
2. 后台任务解析 CSV → 在**同一 `REPEATABLE READ, READ ONLY` 事务**里取出该结算日的
   库内订单 → 计算差异 → 发布报告；
3. 「已发布报告」区按结算日查看当前有效报告。

页面可直接下载**含差异的样例 CSV**
（`app/static/samples/channel_2026-11-20.csv`，对应结算日 2026-11-20），
上传后可看到：10 单一致、4 单字段不符（金额/手续费/商户/金额+手续费）、
2 单库内独有、2 单渠道独有、2 个同号冲突（库内重复 1 个、CSV 重复 1 个）。

### 核对规则

- 按 `order_no` 对齐两侧；
- **任一侧同号重复 → 冲突**：两侧原始行全部列出（渠道侧带 CSV 行号），
  不做任意配对，也不参与独有/不符判定；
- 仅渠道有 → 渠道独有；仅库内有 → 库内独有；
- 两侧各一行但商户、金额或手续费不同 → 字段不符，并标出具体不符字段；
- 金额、手续费按数值精确比较（`Decimal`），`12.3` 与 `12.30` 视为相等。

### 快照与发布语义

- **同一快照**：每次核对的全部查询共享一个可重复读只读事务快照，
  核对期间其他连接补记的订单（页面「补记订单」可随时写）不会混入报告；
- **连续上传**：同一结算日可连续提交，新报告完整发布前旧报告仍可查看；
- **不乱序覆盖**：任务按提交时刻获得递增序号，仅当序号大于该结算日
  已发布报告的序号时才替换；较晚提交的任务发布后，先提交的迟到任务
  完成时标记「未覆盖（迟到）」，报告保持不动；
- **失败保留旧报告**：CSV 解析、数据库查询或发布任一环节失败，任务标记
  失败并在任务列表显示原因，已发布的旧报告原样保留。

### 补记订单

「补记订单」卡片可向 `settlement_orders` 写入指定字段的一笔订单
（商户必须已存在）。典型演示：上传样例 CSV 看到 `CH20261120-101` 为渠道独有
→ 补记该单 → 重新上传同一 CSV → 差异消失。

## SQL 计划对照（保留功能）

提交一条只读 SELECT 后，后台开一条**专用连接**，在同一个
`REPEATABLE READ, READ ONLY` 事务里执行 4 次 `EXPLAIN (ANALYZE, FORMAT JSON)`：

| 顺序 | 轮次 | 设置 |
|----|----|------------------------|
| #1 | 1  | 默认（enable_nestloop=on） |
| #2 | 1  | 关闭嵌套循环（=off）       |
| #3 | 2  | 关闭嵌套循环（=off）       |
| #4 | 2  | 默认（=on）               |

第二轮颠倒顺序，抵消缓存预热偏差；四次执行共享同一事务快照，期间其他
连接照常写入也不影响本批。

结论判定：两轮快慢结论相反、或两种设置计划结构相同（节点类型/扫描关系/
索引/连接策略一致，忽略数值）→「无法判断改善」；两轮一致 → 给出
「关闭嵌套循环更快 / 默认计划更快」；超时、取消或报错 → 不给结论。

运行约束：同时只运行一批（满额 409）；单次执行 `statement_timeout = 10s`，
另有 15 秒客户端兜底（断开连接确保 SQL 停止）；「取消」通过
`pg_cancel_backend` 让 SQL 真正停下；名额在 SQL 停止、事务结束、连接关闭
后才释放。输入校验：仅单条只读 SELECT（sqlparse 静态检查 + READ ONLY 事务双保险）。

## 样表数据

- `merchants`：5000 个商户，类别 A 只有 100 个；
- `settlement_orders`：100 万行随机订单（类别 A 的 100 个商户沉淀 70 万单，
  用于计划对照演示），结算日分布在 2026-08-01 ~ 2026-11-13；
- 另有 2026-11-20 的 19 行**确定性对账演示订单**（`CH20261120-*`），
  与样例 CSV 一一对应。数据库关闭并行查询
  （`max_parallel_workers_per_gather=0`），模拟迁库后实例未开并行的场景。

## API 一览

### 流水核对

| 方法 | 路径 | 说明 |
|-----|------|------|
| POST | `/api/recon/tasks` | 上传 CSV 创建核对任务（multipart：`settle_date` + `file`） |
| GET  | `/api/recon/tasks` | 任务列表（含失败原因 / 统计） |
| GET  | `/api/recon/reports` | 各结算日已发布报告摘要 + 最新任务状态 |
| GET  | `/api/recon/reports/{settle_date}` | 该结算日当前有效报告（含全部差异行） |
| POST | `/api/orders` | 补记一笔订单（`order_no/merchant_id/amount/fee/settle_date`） |

### 计划对照

| 方法 | 路径 | 说明 |
|-----|------|------|
| POST | `/api/batches` | 提交对照批次（409=繁忙，400=SQL 校验失败） |
| GET  | `/api/batches` | 批次列表（不含完整计划 JSON） |
| GET  | `/api/batches/{id}` | 批次详情（含 4 次计划 JSON 与结构摘要） |
| POST | `/api/batches/{id}/cancel` | 取消运行中的批次 |
| POST | `/api/sample-row` | 向 `settlement_orders` 补记随机一行 |

## 目录结构

```
├── docker-compose.yml
├── db/init.sql            # 结算样表 + 倾斜数据 + 对账演示数据
└── app/
    ├── Dockerfile
    ├── main.py            # FastAPI 入口（核对 + 对照 + 补记 API）
    ├── recon.py           # 核对核心：CSV 解析、差异计算、任务/报告仓库（纯标准库）
    ├── reconrun.py        # 核对执行器（同一快照取数、按序号守卫发布）
    ├── runner.py          # 对照批次执行器（单事务 4 次执行、限时、取消、名额管理）
    ├── plans.py           # 计划结构归一化 + 结论判定
    ├── sqlcheck.py        # 只读 SELECT 校验
    ├── store.py           # 内存批次仓库
    └── static/
        ├── index.html / app.js / style.css   # 网页（流水核对 + 计划对照两个标签页）
        └── samples/channel_2026-11-20.csv    # 含差异的样例渠道 CSV
```

> 说明：该工具面向受信任的内网用户，计划对照输入的 SQL 会被直接执行
> （只读事务保护），请勿暴露到公网。任务与报告保存在内存中，重启即清空。
